# Test policy and migration evidence

Runtime Python must retain strictly more than 95% line coverage globally and for every production module; branch coverage is informational. A module at or below its floor fails even when the total passes. Coverage counts must be consistent, and empty or invalid reports fail closed. Authentication, migrations, setup/unload, live windows and replay require behavioral regressions. Defensively mocked failure cases remain when deleting them would remove distinct regression protection. No file is removed merely to reduce the test count.

The practice and next-race suites now load complete bundled JavaScript modules in Node. Browser/Lit boundaries are simulated only in unit tests; Chromium tests render the real modules and Lit implementation. Test inputs and meaningful assertions were preserved. Exact source checks for installation calls, breakpoint constants and one CSS media-query layout were removed: full-gallery keyboard/actions checks, locale/time-zone checks and mobile/tablet/desktop visual tests cover those user behaviors. Other older Python-driven card regressions remain until equivalent direct-module coverage replaces their assertions; Node is required, so they cannot silently disappear in CI.

The duplicate translation-key/source-installation checks in `test_phase_5_quality.py` were removed. Translation schema and placeholder parity use one validator; browser tests retain localization, fallback and action coverage. Timing-budget tests run weekly rather than blocking ordinary PRs. The live-window recovery test drives its retry loop with controlled time instead of waiting 20 real seconds. Timer cleanup fixes preserve assertions while satisfying HA 2026.9's lifecycle checks.

Control tools have separate offline tests for invalid audit responses, bounded retries, coverage measurement, branch routing and aggregation, release recovery, pagination/idempotence and safe Git synchronization. The installed-ZIP smoke test uses real HA, coordinators, entities and WebSocket handling, with external HTTP responses simulated. It verifies the packaged import path, a TrackStatus update, discovered entity IDs and unload. Use `python scripts/test_installed_release.py --archive /path/to/f1_sensor.zip --version <expected-version>` to test a downloaded draft or published artifact, with its adjacent `.sha256` and `.spdx.json` files. This validates the original archive and extracts its exact bytes without rebuilding or changing it. Without `--archive`, the normal CI check builds and verifies a temporary archive from the checkout. Neither mode claims live F1 network or physical-dashboard validation.

During rollout, main/content keep the older stable test baseline until normal code promotion, as explicitly agreed. Their CI bootstrap and legacy content verifier must be replaced by the full dev implementation during that promotion; never carry the legacy workflow or lower test baseline back into dev/beta.

PR check reuse is limited to two-hour-old successful development pushes in this repository with identical complete Git trees. GitHub's run/job API is the evidence source; contributor artifacts and check names from other workflows are never accepted. Every matrix profile must pass. Revalidation rejects changed attempts, expired evidence, missing jobs, skipped jobs and failed jobs. Release verification and scheduled maintenance always execute fresh checks. Offline regressions exercise these boundaries and push/PR routing fallback.

Target-language-only changes use the translations lane rather than the runtime coverage suite. Both nested integration catalogs and flat card catalogs use the same structural validator: duplicate or unknown keys, blank or invalid values, and incorrect placeholder names fail. Missing target keys are allowed. Tests derive expected real-language values from independent catalog reads and use synthetic sentinel catalogs to prove region-to-base-to-English fallback, language selection and action wiring. Neither translated prose nor a fixed language count is an API contract. Source-language, loader, schema and test-tool changes retain broader verification.

Local and remote wrappers use `scripts/verification.py` for executable check commands. The local preflight validates repository-pinned tool versions, clean dependency installation, the locked browser, workflow syntax and manifest order. Full and release profiles include the security gate. Unknown Git comparisons cannot produce an empty successful plan. Success is recorded against the complete source fingerprint and installed tool/dependency metadata, and source or environment drift during a run invalidates it. Local evidence explicitly leaves GitHub merge-result verification and HACS/hassfest pending.

Development dependency changes block newly introduced high or critical security exposure relative to an immutable base lockfile. Release promotions and policy changes use the full high/critical gate; daily health checks apply it independently to all three code branches. Low/moderate findings are warnings. Active expired scoped exceptions fail, while unused expired exceptions do not. Registry or malformed-response failures remain distinct from vulnerability policy failures.

Push verification never defers to queued or successful PR-head evidence: PRs test merge results, which may differ. Metadata edits do not restart code checks; target changes do. Documentation delivery uses separate workflows and immutable verified commits for both channels, so publication failures cannot masquerade as product-test failures. Cleanup treats an already missing merged branch as an idempotent success without hiding permission errors or deleting an advanced branch.

The independent documentation publisher starts on pushes to `beta` and `main`, using the workflow version on that branch. It waits for successful release verification of the exact same commit before resolving immutable publication sources. The first promotion to `beta` can therefore update beta documentation while `main` still has the older publication workflow; no main-first activation or temporary fallback is required. Waiting does not hold the shared Pages deployment lock. Superseded pushes and failed verification do not publish. Missing verification times out as a separate delivery failure; rerun Documentation publication after verification succeeds. Publishing documentation never publishes a release draft.
