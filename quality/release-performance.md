# Release-candidate performance evidence

The release profiles are defined before measurement in `custom_components/f1_sensor/tests/fixtures/release_performance_budgets.json`. They supplement the existing small Phase 5 microbenchmark; they do not change its budget. The initial 20-driver draft was increased to the current 22-driver field before final acceptance; all preselected limits are unchanged. Run them on the locked release candidate with the current Home Assistant constraints, outside coverage instrumentation unless a profile explicitly measures Python allocations. These are reproducible synthetic inputs through real production stores/transports and local Home Assistant WebSockets, not a claim about a real F1 weekend or a tablet's physical network.

The WebSocket profile uses 1, 3 and 10 separate authenticated local Home Assistant connections. Every connection subscribes to Weekend Hub and Track Map. Twenty-two drivers and sixty completed laps populate the analysis before measuring one hundred timing/position updates. Ten-frame bursts exercise coalescing at the existing 500 ms client throttle. Report initial/reconnect bytes, update bytes per simulated source second, dispatch p95 and elapsed processing/delivery time. The preselected limits are 20 seconds total (including roughly five seconds of throttle waits), dispatch p95 under 50 ms and at most 1 MiB per client per source second. These are conservative regression ceilings, not target bandwidth or a recommendation to poll faster. Connection closure and entry unload must release the tested hubs, listeners and owned tasks.

The replay profile covers two synthetic two-hour sessions with twenty-two drivers and one timing frame per source second. Ninety-second laps exercise bounded lap/strategy/timeline stores while repeated frames exercise the disk reader, JSON decoding and dispatch. Input is written incrementally to disk. Playback waiting is advanced deterministically; the test does not spend four wall-clock hours waiting. Include pause/resume, middle-session seek, session replacement and final unload. Record disk size, elapsed processing, Python allocation peak and retained allocations after each cleanup. Initial budgets are at most 96 MiB of fixture disk, 120 processing seconds per full session, 64 MiB peak Python allocations, 8 MiB retained growth between sessions and 16 MiB retained after unload. Allocation measurements are distinct from process RSS and do not claim total Home Assistant memory use.

Do not raise a budget after observing a failure to make the candidate pass. First determine whether the fixture, environment or production code explains it; record any justified profile revision separately. Live source/auth and real-dashboard validation remain separate release gates.
